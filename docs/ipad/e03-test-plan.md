# E03 acquisition, migration, and maintenance acceptance

Issue: [#4](https://github.com/mooneeb/bookorbit/issues/4). Parent: [#1](https://github.com/mooneeb/bookorbit/issues/1).

The acceptance boundary is the actual native app and web app connected to an isolated BookOrbit HTTP server, migrated PostgreSQL database, and temporary source files. Assertions use visible UI, public authenticated API responses, and delivered/exported artifacts. Database writes occur only during fixture setup. Controlled Torznab, qBittorrent, Prowlarr and migration-provider endpoints replace external services; they do not replace BookOrbit services, persistence, permissions, or source publication.

## Commands

`pnpm ipad:test:e03:list` lists the implemented HTTP suites. `pnpm ipad:test:e03` creates a fresh fixture and runs HTTP suites sequentially. Add `--e03-case=A01` through `A05` to select a QA case. `pnpm ipad:test:e03:ui` additionally discovers implemented `testIPADE03*` XCUITest methods and executes them through the production BookOrbit scheme. `IPAD_TEST_ONLY` can select one exact method. `pnpm ipad:test:e03:web` runs the real E03 Playwright suites with one worker and zero retries.

For development, `pnpm ipad:serve:e03` retains the isolated API at `http://localhost:16482/api/v1`. Add `--web` to retain the built web app at `http://localhost:16484`. Once startup completes, source `test-results/ipad/<runID>/e03-runtime.env` before `pnpm ipad:test:e03:http:retained` or a feature-specific test. This private, mode-0600 file holds runtime fixture configuration and must not be published. The public manifest `e03-fixture.json` supplies content paths and IDs. Keep one shared native simulator sequence, protected by `/tmp/bookorbit-ipad-xcode.lock`; do not overlap native suites or source-file writers.

## Fixtures and isolation

The existing large library retains 50,000 books inserted in 500-row batches, an actual source PDF, EPUB, comic, and audio samples. E03 adds a bounded import destination named `Fixture library`, a separate `E03 scan fixture` folder with one PDF, a simulator Files document named `E03 upload.pdf`, a missing PDF row with original byte size and KOReader-compatible partial MD5, an identical repair candidate, and a separate duplicate-merge pair. The native runner installs the app once and copies the upload document into its public Documents directory before exercising the real Files picker.

Roles are distinct: the owner is a superuser; the editor has library metadata edit, upload, download and Book Dock access; the reader has library viewing/download and request access; the restricted reader has no library access; the settings operator is a non-superuser with app-settings and request access; the request moderator has request moderation and request access; the maintainer has library management, metadata edit, deletion and download. These grants preserve specific permission checks instead of treating every administrator as a superuser.

Book Dock automatic metadata fetching and automatic finalization are disabled. Request credentials are encrypted with a generated, per-run key. The retained protocol source delivers an actual PDF through the real request pipeline. Provider credentials and fixtures stay local. Each destructive suite owns and cleans up its new records where possible. Run a fresh fixture for independent native acceptance after destructive HTTP tests, or explicitly recreate the consumed feature fixture before continuing.

## Residual checks and completion limits

Physical iPad QA remains necessary for third-party Files-provider access, real home-server folders/private networking, live source/client/provider credentials, actual animation feel, VoiceOver usability, hardware audio behavior, and installation/signing refresh. The integrated human walkthrough must cover all five QA steps using the resulting real files and external/web state. Browser viewport emulation does not prove native execution. Protocol fixtures do not prove live credentials. Screenshot capture does not prove a reviewed visual comparison. No complete issue-closure claim is permitted while required repeatable UI/artifact behavior or these explicitly required acceptance gates remains unverified.
