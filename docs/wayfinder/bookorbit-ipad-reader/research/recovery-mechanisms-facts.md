# Recovery mechanism facts

Research date: **2026-10-23**. Evidence for [Set library scale, storage, backup, and export requirements](https://github.com/mooneeb/bookorbit/issues/12), planning branch `BO-12-storage-backup-export`, published baseline `a46051434369d8c0e699e38f1795c1a6e3559750`. Factual research only. **Documented** identifies primary API/docs/source; **inference** identifies an integration consequence. No build, device experiment, backup, restore or performance measurement was performed.

## Feasible mechanism, conditional on product choices

Subsequent [live choices](https://github.com/mooneeb/bookorbit/issues/12#issuecomment-6371518636) select **unencrypted app recovery files**, notes/context plus the download list, seven daily/four weekly server points and a 20-book iPad validation set. The [operational round](https://github.com/mooneeb/bookorbit/issues/12#issuecomment-6371711106) selects restic for the separate server repository and a five-minute write-pause bound. The encrypted AppleArchive path below is an investigated alternative, not the chosen app format. AppleArchive's encode/file stream APIs remain useful without an encryption stream; the complete policy is recorded separately in [Storage, backups and recovery](../decisions/storage-recovery.md).

**Recommendation:** if password protection is chosen, use the system **Apple Archive inside Apple Encrypted Archive (AEA)** with its built-in password/scrypt profile. It supplies archive encoding, compression and authenticated encryption without selecting custom cryptography. Stream a credential-free GRDB backup and immutable assets into a locally staged, seekable encrypted file, then export the completed file to Files. The relevant Swift encryption APIs date from iPadOS 15 and fit the selected minimum **iPadOS 26.0**, supplied current **26.6.1** device and Swift 6 stack. This is API feasibility, not a tested BookOrbit round trip. [Apple encryption context](https://developer.apple.com/documentation/applearchive/archiveencryptioncontext), [password profile](https://developer.apple.com/documentation/applearchive/archiveencryptioncontext/profile-swift.struct/hkdf_sha256_aesctr_hmac__scrypt__none), [selected stack](../decisions/native-stack.md).

For a simple self-hosted deployment, **a coordinated PostgreSQL logical snapshot plus protected file capture, stored with restic**, is a feasible candidate to evaluate. Neither tool coordinates BookOrbit's database and external files. Database size, acceptable interruption and measured restore time may instead justify PostgreSQL base backups plus WAL archiving. No mechanism here selects password policy, optional backup contents, retention counts, byte limits or recovery-time targets.

The live issue requires app recovery including local notes, editable ink, saved context and unsynced/conflicting changes; daily server backups outside primary storage with at most 24 hours of synced-work loss; and manually emptied Trash without automatic expiry. It does **not** require a new human-readable PDF/text export. The subsequent choices cited above settle contents/protection/retention and override any conditional alternative below; the mechanisms themselves do not decide those policies. [Accepted priorities](https://github.com/mooneeb/bookorbit/issues/12#issuecomment-6371410842).

## AppleArchive: exact APIs and limits

**Documented:** create `ArchiveEncryptionContext(profile:compressionAlgorithm:compressionBlockSize:)` with `.hkdf_sha256_aesctr_hmac__scrypt__none`, then call **`try context.setPassword(password)`**. This is the password mode. The `.hkdf_sha256_aesctr_hmac__symmetric__none` profile instead takes **`try context.setSymmetricKey(SymmetricKey)`**; a generated key alone does not provide recovery from a remembered password. `generatePassword() throws -> String` and `generateSymmetricKey() throws -> SymmetricKey` also exist. Prefer the throwing setters when handling invalid credentials. The scrypt profile uses HKDF-SHA256 and AES-CTR/HMAC-SHA256 authenticated encryption, with no separate digital signature. Its `none` suffix does not mean unencrypted. [Password API](<https://developer.apple.com/documentation/applearchive/archiveencryptioncontext/setpassword(_:)>), [key API](<https://developer.apple.com/documentation/applearchive/archiveencryptioncontext/setsymmetrickey(_:)>), [profile constants](https://developer.apple.com/documentation/applearchive/archiveencryptioncontext/profile-swift.struct), [SDK definitions](#sdk-evidence).

The supplied SDK says an internal password byte-length range is enforced and the caller must enforce strength. The reviewed public Swift interface exposes no scrypt cost/salt tuning parameters; do not invent a minimum length or KDF cost guarantee. A password-encrypted file enables offline password guessing. No platform password-recovery service is established by these APIs. Keep the archive password/key separate from the payload and from BookOrbit authentication credentials. [SDK `AEAContextSetPassword`](#sdk-evidence).

**Documented pipeline:** `ArchiveStream.encodeStream(writingTo:...)` writes archive entries into `ArchiveByteStream.encryptionStream(writingTo:encryptionContext:flags:threadCount:)`, whose destination can be `ArchiveByteStream.fileStream(...)`. Restore opens the file, creates **`ArchiveEncryptionContext(from: stream)`**, supplies `setPassword`, then creates **`ArchiveByteStream.decryptionStream(readingFrom:encryptionContext:flags:threadCount:)`** and an archive decode stream. These stream constructors are failable. Check write/read errors and throwing close operations; `close(updatingContext:)` seals and returns container attributes. Apple's WWDC21 example uses this composition. [Encoder](<https://developer.apple.com/documentation/applearchive/archivestream/encodestream(writingto:selectusing:flags:threadcount:)>), [context reader](<https://developer.apple.com/documentation/applearchive/archiveencryptioncontext/init(from:)>), [decryptor](<https://developer.apple.com/documentation/applearchive/archivebytestream/decryptionstream(readingfrom:encryptioncontext:flags:threadcount:)>), [close](<https://developer.apple.com/documentation/applearchive/archivebytestream/close(updatingcontext:)>), [WWDC21 session 10233](https://developer.apple.com/videos/play/wwdc2021/10233/).

Important boundaries:

- **Seekable encrypted output:** `AEAEncryptionOutputStreamOpen` requires destination `pwrite`; the returned plaintext-facing stream is sequential-write only. Sequential decryption needs sequential input. Thus streaming avoids loading the complete backup into `Data`, but does not establish a write-only pipe directly to an arbitrary Files provider. Stage a local random-access file, successfully close it, then hand off the finished artifact. The online Swift `encryptionStream(writingTo:...)` page currently contains misleading decryption prose; the SDK header and Apple's example establish output direction. [SDK `AEAStreams.h`](#sdk-evidence), [Apple example](https://developer.apple.com/videos/play/wwdc2021/10233/).
- **Memory is not automatically bounded:** the initializer's default compression block size is `1 << 20`; `threadCount: 0` requests defaults. The C setter internally clamps block sizes without publishing the effective range. Random-access decryption defaults to `allocationLimit: Int.max`; even its requested allocation limit may be exceeded for compressor/block requirements according to the header. Prefer sequential processing and explicitly bounded worker/buffer choices; measure the resulting working set. There is no verified maximum archive size, memory ceiling or throughput for this app/device. [Initializer](<https://developer.apple.com/documentation/applearchive/archiveencryptioncontext/init(profile:compressionalgorithm:compressionblocksize:)>), [random-access API](<https://developer.apple.com/documentation/applearchive/archivebytestream/randomaccessdecryptionstream(readingfrom:encryptioncontext:allocationlimit:flags:threadcount:)>), [SDK evidence](#sdk-evidence).
- **Metadata privacy:** `authData` is available before unlocking; the header explicitly calls it unencrypted. Keep note titles, account details, manifests and other private contents inside the encrypted payload. Password protection does not hide the encrypted file's existence/length. [Auth data](https://developer.apple.com/documentation/applearchive/archiveencryptioncontext/authdata), [SDK `AEAContext.h`](#sdk-evidence).
- **Interoperability:** these are Apple APIs with an Apple archive format, not ZIP/password-ZIP or a documented Linux/browser recovery contract. The reviewed Apple sample is a macOS sample; individual API availability, rather than that sample's target, establishes iPadOS support. A native recovery file can preserve arbitrary bytes, but non-Apple extraction and third-party editable PencilKit support remain unverified. Do not promise them. [Directory sample](https://developer.apple.com/documentation/applearchive/encrypting-and-decrypting-directories), [context availability](https://developer.apple.com/documentation/applearchive/archiveencryptioncontext).

**Inference: bounded, safe import still belongs to BookOrbit.** Decode headers before materialization and allow only the versioned recovery layout and ordinary files/necessary directories. Reject absolute paths, `.`/`..`, duplicate or normalization-colliding paths, symbolic links, hard-link/clone metadata and special entries. Write into a new private staging root with containment/no-follow checks, never directly over the live store. Apple Archive can represent symlinks and hard-link/clone relationships; encryption is not a path-safety policy. Header/entry filters and caller-sized `readBlob` buffers provide hooks, but the reviewed APIs do not promise BookOrbit's quotas. [Entry filter](https://developer.apple.com/documentation/applearchive/archiveheader/entryfilter), [decoder](<https://developer.apple.com/documentation/applearchive/archivestream/decodestream(readingfrom:selectusing:flags:threadcount:)>), [SDK archive fields and stream protocols](#sdk-evidence).

Set and enforce limits on the input file, prologue/header/manifest sizes, entry/path count and lengths, per-entry decoded bytes, aggregate expansion, database size, image pixels, workers, time/cancellation and staging disk consumption. Count actual decoded bytes as well as declared sizes. The context reader consumes the archive prologue before credentials are supplied, so outer-file limits and parser exposure still matter. Authenticate/validate the complete archive and all expected asset lengths/hashes before publishing the restored store. A valid password/MAC does not establish compatible schema, safe content or correct note references. Exact limits remain unselected. [Context creation contract](<https://developer.apple.com/documentation/applearchive/archiveencryptioncontext/init(from:)>), [SDK evidence](#sdk-evidence).

**CryptoKit comparison:** `AES.GCM.seal(_:using:nonce:authenticating:)` accepts a message and `SymmetricKey`, returning a `SealedBox`; this is not an archive stream or password-recovery format. A bounded chunked container would additionally need an established password KDF, nonce management, authenticated ordering/length/finalization and truncation handling. AppleArchive already provides the relevant container/password mechanism, so no custom CryptoKit framing is selected or needed by this research. [CryptoKit seal API](<https://developer.apple.com/documentation/cryptokit/aes/gcm/seal(_:using:nonce:authenticating:)>).

## Editable originals and a consistent GRDB capture

**Documented:** `PKDrawing.dataRepresentation()` returns the entire drawing; `PKDrawing.init(data:) throws` restores serialized drawing data. Therefore archive the original bytes unchanged, alongside matching PNG/context and revision/hash/provenance manifests. Restoring a PNG cannot restore editable strokes. Keep required PencilKit content version and app/schema/OS provenance, and preserve unsupported original bytes instead of silently flattening or downgrading them. The selected stack caps PencilKit content at **version 4**, supported from iPadOS 26. Serialized drawing creation/decoding is itself a whole-drawing `Data` boundary, even when the outer archive streams. [Serialization](<https://developer.apple.com/documentation/pencilkit/pkdrawing-swift.struct/datarepresentation()>), [restoration](<https://developer.apple.com/documentation/pencilkit/pkdrawing-swift.struct/init(data:)>), [content version 4](https://developer.apple.com/documentation/pencilkit/pkcontentversion/version4), [native-stack contract](../decisions/native-stack.md#ink-previews-and-saved-context-formats).

**Documented, pinned GRDB 7.11.1, released 2026-06-18:** `DatabaseReader.backup(to:pagesPerStep:progress:) throws` works with `DatabaseQueue` and copies to a separate `DatabaseWriter`. Default `pagesPerStep` is `-1`, copying all pages in one step. A positive page count permits progress/cancellation callbacks between steps, but the synchronous method still blocks its calling thread until completion. Its implementation uses `sqlite3_backup_init/step/finish` for the `main` database; this does not capture external files or independently attached databases. A callback error on the completed step is ignored, so it cannot be the final archive validation gate. Run this away from UI work and close the destination before archiving it. [Release](https://github.com/groue/GRDB.swift/releases/tag/v7.11.1), [exact reader API](https://github.com/groue/GRDB.swift/blob/v7.11.1/GRDB/Core/DatabaseReader.swift#L316), [implementation](https://github.com/groue/GRDB.swift/blob/v7.11.1/GRDB/Core/Database.swift), [SQLite backup contract](https://www.sqlite.org/c3ref/backup_finish.html).

SQLite documents a completed online backup as a consistent database snapshot. GRDB warns that concurrent `DatabasePool` writes may or may not appear in a backup; that warning does not mean a completed backup is a torn database. The selected single serialized `DatabaseQueue` routes its read/backup through its serial writer queue and isolation, blocking that queue's writes during the capture. Do not describe page stepping as allowing those same-queue writes to interleave. [SQLite backup overview](https://www.sqlite.org/backup.html), [GRDB reader](https://github.com/groue/GRDB.swift/blob/v7.11.1/GRDB/Core/DatabaseReader.swift), [queue read implementation](https://github.com/groue/GRDB.swift/blob/v7.11.1/GRDB/Core/DatabaseQueue.swift).

`DatabaseSnapshot` is different: it is a live read-only connection holding an unchanging database view, ordinarily obtained from `DatabasePool.makeSnapshot()`, not a durable exported file. Its source explicitly says a non-WAL snapshot blocks database modifications for its lifetime. Do not assume it supplies cheap concurrent snapshots for the selected rollback-journal `DatabaseQueue`, or switch to WAL just to name a backup a snapshot. GRDB 7.11.1's manifest requires Swift tools **6.1**; “Swift 6” alone should not be interpreted as Swift 6.0 compatibility. The selected Swift 6.4 toolchain satisfies that declared requirement; compilation was not tested here. [Snapshot source](https://github.com/groue/GRDB.swift/blob/v7.11.1/GRDB/Core/DatabaseSnapshot.swift), [package manifest](https://github.com/groue/GRDB.swift/blob/v7.11.1/Package.swift), [selected journal/toolchain](../decisions/native-stack.md).

**Inference: asset reference leases remain necessary** whenever writes/collection resume before referenced asset bytes are captured. A SQLite snapshot cannot stop collection of a now-replaced drawing file. Establish backup protection under the same serialization/lease boundary as publication and collection **before the snapshot cut**, derive a bounded/paged required-asset set from that frozen database, and retain protection until every referenced byte is in stable backup staging or the completed archive. An alternative is to keep all relevant mutators/collection paused through capture, at an unmeasured availability cost. Neither method is implemented or benchmarked here. Preserve the accepted assets-before-reference ordering and verify hashes, not just file presence. [Existing asset/publication contract](../decisions/offline-sync.md#asset-transfer-and-atomic-publication), [note retention invariant](../decisions/note-model.md).

The format can carry stable note/source identities, typed content, original/PNG/context bundles, manifests, conflict/recovery candidates, a consistent local database, and pending operations/receipts/checkpoints/dependencies. Capture one verified account/server scope. Exclude Keychain, passwords, access/refresh tokens, cookies, Authorization headers and credential-bearing transport configuration. Raw database backup is not a redaction API: it is suitable only when the captured store is verified credential-free; otherwise create a validated recovery projection. Reconstruct transport after sign-in while preserving immutable operation bytes/UUIDs/digests. Whole book downloads and other optional contents remain separate product choices. [Local-store/credential boundary](../decisions/native-stack.md), [operation and account contract](../decisions/offline-sync.md#scope-durable-local-state-and-operation-identity).

## Restoring bytes does not authorize replay

The existing sync specification requires these integration behaviors, independently of archive/database tooling:

- **iPad recovery:** stage and validate before switching stores; preserve local/recovered/conflicting work. Reauthenticate the original account/server and reconcile device incarnation, sequence, operation UUID/digest, uncertain receipts, replay floors, dependencies, lifecycle and current heads before sending restored pending work. A rolled-back counter, missing receipt or expired cursor does not prove an operation never ran. Importing one iPad backup is not itself a reason to rotate the server's generation for every device.
- **Server recovery:** after coordinated database/asset restoration, explicitly rotate the **sync recovery generation** before ordinary sync resumes and require full reconciliation. Restoring the previous server UUID/credentials cannot detect the rollback automatically. Never blindly replay pre-restore pending mutations, resurrect permanent deletions or overwrite newer iPad work. Recovery-generation management is an app runbook step, not a `pg_restore` or restic feature.

These are consequences of the confirmed [scope/identity](../decisions/offline-sync.md#scope-durable-local-state-and-operation-identity), [receipt barriers](../decisions/offline-sync.md#retry-results-and-durable-acknowledgments), [generation rotation](../decisions/offline-sync.md#change-feed-and-long-offline-recovery) and [deletion rules](../decisions/offline-sync.md#trash-permanent-deletion-and-restoration), not new retention decisions.

## Free self-hosted server primitives

**PostgreSQL 18:** `pg_dump` produces an internally consistent logical snapshot even while ordinary reads/writes continue. It covers one database; roles/tablespaces require separate treatment, such as `pg_dumpall --globals-only`. Custom/directory formats support `pg_restore`; synchronized `--snapshot` coordinates database sessions, not independent files. PostgreSQL 18's manual also cautions that dumps are generally unsuitable for regular production backups outside simple cases. Dumps do not supply WAL/PITR. Base backups plus a continuous WAL archive are the documented alternative, with additional administration/storage and version coupling. Match dump/restore tooling and extension availability to the deployed server; `pg_dump` refuses newer server major versions. [SQL dump](https://www.postgresql.org/docs/18/backup-dump.html), [pg_dump reference and caveat](https://www.postgresql.org/docs/18/app-pgdump.html), [WAL/PITR](https://www.postgresql.org/docs/18/continuous-archiving.html).

**restic 0.19.1, released 2026-07-05**, supplies these mechanisms; release-tagged documentation is the evidence, not a claim that it is installed:

- **Storage/encryption:** local, SFTP and self-hosted REST repositories are supported. Repository data/metadata are encrypted and authenticated with AES-256-CTR/Poly1305-AES; scrypt protects access to repository master keys. Keep repository access/password material recoverable separately. Free software does not provide free off-server storage. [Repository setup](https://github.com/restic/restic/blob/v0.19.1/doc/030_preparing_a_new_repo.rst), [cryptography/design](https://github.com/restic/restic/blob/v0.19.1/doc/design.rst), [release](https://github.com/restic/restic/releases/tag/v0.19.1).
- **Deduplication:** content-defined chunks let successive snapshots reuse existing content. This is a storage mechanism, not a verified savings ratio or runtime bound for books, compressed dumps or encrypted app recovery files. [Backup/chunking design](https://github.com/restic/restic/blob/v0.19.1/doc/design.rst#backups-and-deduplication).
- **Checks:** default `check` validates repository structure; **`check --read-data`** additionally reads/verifies all pack data. `--read-data-subset` can spread data checks over runs; random subsets do not guarantee eventual complete coverage. These checks do not open BookOrbit or assert drawing editability, reference completeness or replay safety. [Versioned check documentation](https://github.com/restic/restic/blob/v0.19.1/doc/045_working_with_repos.rst#checking-integrity-and-consistency).
- **Retention:** `forget` removes snapshot references according to selected `--keep-*` rules; `prune` reclaims unreferenced repository data. Dry-run is supported. Pruning needs planned resources/time and can block backups. These commands do not implement live-app Trash rules; no retention count is selected here. [Versioned retention documentation](https://github.com/restic/restic/blob/v0.19.1/doc/060_forget.rst).
- **Restore and errors:** restore a named snapshot to a separate target, optionally selecting files; ordinary restore can overwrite existing targets. `backup` exit code **3** means an incomplete snapshot because source files could not all be read, not complete success. `--stdin-from-command` checks the producer's exit status; plain `--stdin` cannot establish that a failed dump produced complete input. Neither approach coordinates the accompanying asset set. [Restore](https://github.com/restic/restic/blob/v0.19.1/doc/050_restore.rst), [backup/exit-status documentation](https://github.com/restic/restic/blob/v0.19.1/doc/040_backup.rst).
- **License:** restic is **BSD 2-Clause**, with source/binary notice requirements. PostgreSQL's permissive **PostgreSQL License** permits use/distribution without a fee. Neither requires a paid backup subscription. [restic license](https://github.com/restic/restic/blob/v0.19.1/LICENSE), [PostgreSQL license](https://www.postgresql.org/about/licence/).

**Inference: one successful restic snapshot still does not make database plus files atomic.** restic scans independent files; `pg_dump` freezes only database visibility. A snapshot can be internally intact while containing metadata for a deleted/missing or different book file. A feasible coordinated capture must either quiesce every relevant writer/collector, including external book-file modification, or use appropriate coordinated filesystem snapshots plus an explicit database recovery method. Immutable note assets can instead be protected by a manifest/reference lease spanning the database cut and file capture. Whole mutable book libraries need additional coordination; note-asset immutability does not extend to arbitrary `/books` files. PostgreSQL itself requires shutdown or suitable consistent snapshots/backup procedures for physical data files; copying a live `PGDATA` tree with restic is not sufficient. [restic scan model](https://github.com/restic/restic/blob/v0.19.1/doc/design.rst#backups-and-deduplication), [PostgreSQL filesystem backup constraints](https://www.postgresql.org/docs/18/backup-file.html), [BookOrbit publication invariant](../decisions/offline-sync.md#asset-transfer-and-atomic-publication).

**Existing source gap:** the pinned production compose uses `pgvector/pgvector:pg18` and separate PostgreSQL, app-data and books mounts. Inspection of compose, workflows and server sources found no complete BookOrbit coordinated backup/restore workflow. The Audiobookshelf backup connector is an importer for another product's backup, not this feature. No statement here certifies the current deployment. [Pinned compose](https://github.com/mooneeb/bookorbit/blob/a46051434369d8c0e699e38f1795c1a6e3559750/docker-compose.yml), [existing import connector](https://github.com/mooneeb/bookorbit/blob/a46051434369d8c0e699e38f1795c1a6e3559750/server/src/modules/migration/adapters/audiobookshelf/audiobookshelf-backup.connector.ts).

A **repository integrity check**, a **file/database restore**, and an **application recovery drill** are distinct evidence. The last must establish editable originals, matching previews/context, all references and protected pending/conflicting work, and safe reconciliation after generation rotation. The accepted 24-hour loss target concerns the age of the captured state in the last fully completed, coordinated off-primary backup, not merely a daily job's start or completion time. Scheduling, failed/incomplete-run detection and restore evidence remain implementation/acceptance work; no restore time or performance is verified here.
