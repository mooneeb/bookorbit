# Current book-collapse paths and personal state

Read-only audit for [Choose how book merges preserve notes and personal book state](https://github.com/mooneeb/bookorbit/issues/21), 2026-10-23. Source pin: 40c0ed85755a4860d089327b55d08c121a8f0d10. Findings describe existing code, not the accepted future policy. No merge, device, filesystem mutation, service operation or runtime test was performed.

## Existing identity-collapse paths

| Path                             | Surviving identity and existing behavior                                                                                                                                                                                         | Material limit                                                                                                                                                                                      |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Move collision with merge policy | Keeps the incoming book/file IDs, deletes the destination book, updates paths/library and recalculates primary file from destination settings. Occupied destination filenames are skipped.                                       | Does not transfer the deleted book's complete metadata, extra files, private state or collection memberships. The executor removes its covers, leaving its original content files on disk.          |
| Rename into an existing folder   | Keeps the destination book when normalized title/primary author match and filenames are free. Reparents source file IDs, then deletes the source book; keeps target primary unless missing and later hands over eligible covers. | No complete hash, edition, ISBN or format-equivalence check. Metadata-triggered, explicit and bulk renames can reach it; ebook/audio combinations can qualify.                                      |
| Scanner duplicate-move repair    | Keeps a missing source book and selected source file ID, deletes exactly one viable recently imported candidate book, and adopts the candidate location/metadata.                                                                | Candidate matching uses sampled hash, relative path, different existing absolute path and a 30-minute import window; only one selected file is updated, without combining complete files/histories. |

Sources: [move policy][move-policy], [move database transaction][move-db], [move filesystem execution][move-fs], [folder-rename decision][rename-decision], [normalized title/author][title-author], [folder-rename transaction][rename-db], [scanner selection][scanner-selection], [scanner collapse][scanner-collapse].

The duplicate-management tool scans/dismisses groups; deleting losers calls ordinary book deletion, without a dedicated personal-state merge endpoint. Deletion removes files before database rows, retaining records on partial filesystem failure. Ordinary moves/renames preserve identities when none of the collapse branches runs. Direct filename rename is separate: it calls filesystem rename before its database write without checking destination existence, an inferred overwrite risk rather than an identity merge. ## File equivalence and source evidence

Move duplicate detection accepts an incoming content file matching any stored destination-library file hash. It does not compare complete file sets, format, size or both complete contents. Scanner fingerprints sample one-KiB blocks using MD5. Full SHA-256 verification during cross-filesystem copy checks the copied incoming file against itself, not the other book entry. Thus a move's copy checksum is not evidence that two books or source editions are identical. [Duplicate lookup][duplicate-lookup], [planner match][planner-match], [sampled hash][sampled-hash], [cross-filesystem copy][copy-verification].

The accepted annotation model instead requires verified source versions, stable user-owned associations and retained original context. Independently present library entries remain independent even if bytes match until an explicit merge decision applies. Those contracts are not implemented by the current collapse code. [Identity/source contract](../decisions/note-model.md).

## Authorization, interruption and integration gaps

Move requires LibraryEditMetadata plus source/target library editor access, with superuser bypass and no separate delete permission. Explicit-ID selection checks library access without the content-filter checks used by query selection; destination duplicate lookup also lacks those filters. Folder rename does not independently authorize the target book. Explicit rename checks source editor access; bulk rename requires ManageLibraries and editor access. Current paths do not expose private note bodies through a review, but move preview does expose affected usernames and Kobo counts. [Move controller][move-controller], [selection access][selection-access], [rename access][rename-access], [preview disclosures][preview-disclosure].

Move and folder rename change files before database commit, with best-effort rollback. Covers move after commit. Rename's repository can silently return when its target disappears after filesystem work. Locks are process-local and do not hold both book identities through the entire operation. SQL transactions therefore do not establish an atomic filesystem/catalog/personal-state merge. [Rename ordering][rename-ordering], [missing-target behavior][rename-db], [process-local locks][file-locks].

Move processes sequentially, cancels between books after stream disconnection and stores the cancelled run as completed with a separate cancellation result. Restart marks running jobs interrupted and schedules scans. Stored jobs contain aggregate counts, without durable per-book intent/receipts/retry identity or undo data. Rename scheduling/progress is in memory. Preview samples are bounded, but execution retains the complete selected plan and bulk rename loads/caches the whole library candidate set. [Move execution/restart][move-execution], [job schema][move-job], [bulk library load][bulk-load].

Deleting a losing book cascades through its private book-level state and collection memberships. File-keyed state survives only when its file rows survive. Kobo delivery/entitlement/state/bookmark rows also cascade; normal removal delivery relies on pending snapshot rows, so actual device cleanup cannot be concluded from the collapse path. KOReader links may become null or cascade with lost file rows. [Personal schema][reader-schema], [collection membership][collection-schema], [Kobo schema][kobo-schema], [removal delivery][kobo-removal], [KOReader schema][koreader-schema].

## Personal-state ownership and constraints

The second read-only audit identified these existing owners and projections. A surviving file row does not by itself preserve book-keyed history.

| State                       | Existing identity/shape                                                                                                                                                                                       | Relevant behavior                                                                                                                                                                        |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reading annotations         | User/book-owned integer ID; quote/body/style/origin/star/version; positions unique by annotation/format with optional file. No exact-range/page uniqueness.                                                   | Book deletion cascades annotations, positions and device state; file deletion nulls a position's file link. Read projection can fall back to the current primary file.                   |
| Annotation device identity  | Annotation/source/device key, acknowledged version and deletion acknowledgment. External keys can repeat across books; lookup includes book ID.                                                               | Purge service waits for linked-device deletion acks, while a parent cascade bypasses that service check. Missing identities can lead legacy ingestion to create a new annotation.        |
| Personal book note          | One user/book text body, at most 10,000 characters; update timestamp, no revision/Trash owner.                                                                                                                | Upsert replaces the value; book deletion cascades it. Detail reads only the caller's note.                                                                                               |
| Journal                     | Multiple entries with per-user client UUID uniqueness, body/optional quote/locators, timestamps and Trash. No file/version binding.                                                                           | Book deletion removes active and trashed entries. Same-UUID creation retries return the existing entry; reusing it under another book conflicts. Routes require current book access.     |
| Status and reading attempts | One user/book status with dates/source; attempts preserve date-only history, outcome/origin and soft deletion, at most one active attempt. External attempt identity is unique per user/provider/external ID. | Both cascade. Editing/deleting attempts rebuilds the current status projection from attempts, so independently copying a status scalar does not reconcile its history.                   |
| File reading state          | User/file progress with text/page/audio and device locators, separate narration state, reader preferences and TTS position. Read-aloud mode/TTS voice preferences are user/book-keyed.                        | File-keyed rows survive reassignment but not file deletion; book-keyed settings cascade. There is no verified source-version snapshot in ordinary progress.                              |
| Audiobook progress          | User/book row referring to current file, revision/capture time/operation ID/manifest revision.                                                                                                                | Either book or current-file deletion cascades. Manifest/base-revision API and legacy timestamp writes have different retry behavior.                                                     |
| Ratings/bookmarks           | One rating per user/book; bookmarks have client UUID and CFI/audio uniqueness constraints.                                                                                                                    | Book deletion removes them and bookmark device links. Reparenting colliding rows needs a policy, not an unrestricted FK update.                                                          |
| Collections/smart scopes    | Collection/book membership with insertion order/date; smart scopes are owner-held filter rules.                                                                                                               | Book deletion removes memberships, leaving definitions. Smart-scope results depend on the resulting catalog, personal state and accessible libraries; no stored membership union exists. |
| Sessions/statistics         | Sessions have user/session identity and book/optional file/attempt references; cursors are user/book/source/device. Daily aggregates use user/library/day without book FK.                                    | Book/file deletion removes detail while daily aggregates can survive. Rebuild uses surviving sessions joined to current libraries; no collapse transaction reconciles historical totals. |
| Integrations/delivery logs  | Book-bound Kobo/Hardcover/StoryGraph records; file-bound KOReader mappings/statistics/reset barriers. Email logs can retain null book/file links.                                                             | Cascade/nulling behavior differs. No merge alias or private-review contract reconciles these identities.                                                                                 |

Sources: [annotation projection][annotation-projection], [device identity lookup][annotation-device-lookup], [annotation purge][annotation-purge], [personal-note upsert][personal-note-upsert], [personal-note detail][personal-note-detail], [journal service][journal-service], [attempt projection][attempt-projection], [TTS schema][tts-schema], [audio API][audio-api], [legacy audio writer][audio-legacy], [smart-scope schema][smart-scope-schema], [statistic rebuild][statistics-rebuild], plus the reader/collection/Kobo/KOReader schemas above. Additional integration schemas: [Hardcover][hardcover-schema], [StoryGraph][storygraph-schema], [email logs][email-schema].

Library management permission is not a private-state conflict-resolution grant. Audited private-state routes pass the authenticated user, including for superusers; no cross-user private conflict-resolution route was found. Collections/smart scopes separately permit explicit superuser access to another owner's object. Move's editor/metadata permission differs from ordinary deletion's LibraryDeleteBooks requirement, despite cascading every owner's rows. [Deletion permission][delete-permission], [attempt route][attempt-route], [collection access][collection-access], [scope access][scope-access].

After a library change, surviving-book APIs and Notebook require current library/content access. Global Annotations filters note ownership without the same library filter. Kobo eligibility excludes inaccessible libraries and queues removal through existing snapshots. There is no consistent retained-history access contract in these code paths; preserving a user's private history must remain distinct from granting access to a now-inaccessible complete book. [Book access][book-access], [Notebook access][notebook-access], [annotation owner conditions][annotation-owner], [Kobo eligibility][kobo-eligibility].

Legacy annotation ingestion compares timestamps/device identities, creating canonical records when no identity matches. KOReader resolves hashes against accessible current/history files and user links, and its whole-book review adapter uses date comparison for personal notes. These are not the accepted durable operation receipts or explicit merge aliases. Notebook aggregates existing annotation/journal/bookmark/personal-note owners without creating copies; current annotation exports cap at 5,000 and omit native originals/context/device acks. [Annotation ingestion][annotation-ingestion], [identity resolution][annotation-resolution], [KOReader file lookup][koreader-lookup], [KOReader personal-note writer][koreader-review], [Notebook projection][notebook-projection], [annotation export][annotation-export].

These are static source facts. The required preservation, private-owner review, canonical collision handling, late-offline reconciliation, source verification and durable restart behavior remain planning contracts, not tested production outcomes.
