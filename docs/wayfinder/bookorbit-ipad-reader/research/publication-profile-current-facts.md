# EPUB and PDF publication profiles: current facts

Factual audit on 2026-10-25 for [Define supported EPUB and PDF publication profiles](https://github.com/mooneeb/bookorbit/issues/23), pinned to `26f5830f114045b6188a2c09fb72e9f54c8fc4f9`. A delegated research agent inspected committed source and primary W3C/Apple documentation; the parent assembled this report. No production code, issues, devices, private books, builds or runtime tests were changed or exercised by that audit. Product coverage remains subject to the live decision.

The selected Foliate/WKWebView and PDFKit engines offer credible implementation paths. Their source paths and advertised APIs do not establish that a publication profile passes native rendering, selection, accessibility, offline or browser acceptance. The [preservation evidence limits][evidence-limits] explicitly leave fixed layouts/spreads, obfuscated fonts, RTL/vertical text, large scans and unusual PDF fonts/forms/links/tags unverified.

## Settled inputs

Keep the selected engines, ordinary unprotected files, immutable verified sources, EPUB exact-selected-text notes and PDF page ink. Available book text, notes and controls require VoiceOver support. Image-only pages remain visually readable with an unavailable-text announcement, without an OCR requirement. Publication scripts and unsolicited remote loads are blocked. Complete offline packages, bounded resources and protected local work are already required. These facts describe accepted planning contracts, not implemented production behavior. [Native scope][native-scope], [EPUB containment][containment], [note model][notes], [resource limits][limits].

## Decisions and evidence still required

The live review decides layouts/spreads, writing directions, media/interactive-document coverage, font-fallback expectations and acceptable partial-content behavior. It must distinguish a required profile from an optional/unavailable feature. Mixed reflowable/fixed EPUB and unavailable fixed-layout selection are concrete gaps to expose, rather than silently treating them as ordinary working EPUBs.

Recommendations from the factual audit are proposals: EPUB 2/3 static reflowable content, horizontal LTR/RTL/mixed text, ordinary embedded fonts and the two recognized obfuscation schemes are credible candidates; static text/image/scanned PDFs deserve equal acceptance weight. Broader profiles require their own declared outcome and implementation evidence. At the initial audit, the first product round was unanswered; the supplement below records its subsequently accepted inputs.

Future checks must distinguish visual rendering, text availability, selection/anchoring, accessible reading, navigation, note placement and offline completeness. Missing resources, unsupported encryption, bad glyphs, unreadable sections and unavailable anchors need specific outcomes. Preserve existing notes/local work and the previous complete server revision on failure. A profile failing required available-text accessibility is a failed acceptance check, even if a partial-reading UI remains useful.

No runtime, browser, device, performance or private-library result is established by this report. Existing fixture gates remain completed only within their recorded scope.

## Supplemental facts: static structures, fixed-page bookmarks and existing PDF comments

Follow-up on 2026-10-25 at the same pinned baseline. **Direct facts** below describe primary specifications, Apple/WebKit documentation or inspected committed code. **Inferences** describe consequences for this adapter and the existing contracts. **Unverified** identifies behavior requiring later runtime evidence. This supplement does not select additional publication profiles or resolve unanswered product questions.

The [canonical intermediate comment][scope-round-one] supersedes the earlier historical statement that the first product round was unanswered: Q1-5 now accept both reflowable and fixed-layout EPUB, horizontal LTR/RTL/mixed text with vertical writing outside initial requirements, static PDF reading and notes without interactive workflows, static EPUB with unavailable media identified, and clearly labelled partial reading. Those answers do not imply acceptance of recommendations about mixed layouts, fixed-page scrolling, font fallback, image-only EPUB bookmarks, existing PDF comments or static tables/SVG/MathML. Those are still Q6-11.

### Static tables, SVG and MathML: rendering, source words and alternatives

**Direct facts:** EPUB 3.3 profiles XHTML and supports embedded Presentation MathML and SVG, as well as standalone SVG content documents. Manifest `mathml` and `svg` properties identify relevant content; they do not certify its rendering, selectable text or accessibility. Reading-system requirements explicitly cover visual Presentation MathML rendering and SVG processing. Static mathematical or vector content does not inherently require publisher JavaScript. [Content documents and manifest properties][static-content-spec], [MathML and SVG processing][static-content-processing].

- SVG `<text>`/`<tspan>` contain character data; vector paths or a raster image can depict letters without those character data. SVG selection rules include logical bidi order and operate within a `<text>` element, so separate positioned text elements do not establish one selectable prose range. [SVG text and selection][svg-text-selection]. SVG used through HTML `<img>` is an image processing context with interaction, including text selection inside that image document, disabled. Inline SVG and SVG loaded as a document have different processing contexts. [SVG processing modes][svg-processing-modes].
- SVG `<title>` and `<desc>` supply names/descriptions for accessibility APIs. MathML `alttext` supplies a textual fallback. These are authored alternatives with their own meaning, not proof of a transcription of every pictured word or a selected range in the visible page. [SVG alternatives][svg-alternatives], [MathML fallback attributes][mathml-alternatives].
- Accessible HTML data tables depend on header/data-cell markup and associations such as `scope`, `id` and `headers`. A table that paints correctly, or a flattened sequence of cell strings, does not establish those relationships for assistive technology. [W3C tables tutorial][table-semantics].
- WebKit documents MathML typography support and specific RTL MathML, SVG and table fixes in Safari 26.4. This is engine evidence for implementation paths and version sensitivity, not a BookOrbit WKWebView selection or VoiceOver result. [WebKit release account][webkit-static-structures].

**Pinned code facts:** Foliate retains manifest MIME types/properties and parses XHTML/SVG using their media types before rewriting resource references. This is recognition and browser delegation, not a compatibility check for every SVG/MathML/table construct. The XHTML iframe fallback restores the original parsed body tree because HTML parsing can insert nodes such as `<tbody>` and change persisted CFI paths. The fixed-layout frame path separately assigns `iframe.src`; it does not use that shared fallback. [Manifest projection][parser], [XML resource path][static-resource-loader], [body preservation][body-preservation], [fixed iframe path][fixed-frame-path].

**Inference:** Preserve canonical body structure, namespaces and text boundaries while exposing authored alternatives. Replacing a table/formula with prose or injecting descriptions as body text could change both selection identity and the publication's meaning. An accessible image description can be read as a description without becoming invented source words for an exact-selected-text note. Actual visible text nodes remain candidates for exact ranges, subject to resolving the correct document, boundaries and quote. The existing selection wrapper's trimming and first-document lookup remain gaps for these constructs too. [Canonical note contract][notes], [selection wrapper][selection].

**Unverified:** Inline versus referenced/standalone SVG, MathML token selection and formula speech, table overflow/header navigation, transformed text geometry, and exact range round trips after reload. No source here establishes that every rendered formula or table has a selectable linear equivalent. Q11 still decides the required static structures; it cannot be answered by a manifest flag alone.

### Legacy layout hints, standardized metadata and mixed layouts

**Direct facts:** Apple documents that EPUB 2 used an Apple Display Options file and EPUB 3 moved layout metadata into the OPF; `rendition:layout=pre-paginated` is its EPUB 3 fixed-layout declaration. Its guide also describes fixed layout as global for Apple Books. Kobo's own documentation recognizes both standardized EPUB 3 metadata and the optional `META-INF/com.kobobooks.display-options.xml` fixed-layout flag. These are vendor behaviors, not proof that legacy packaging is standardized EPUB 3. [Apple layout guidance][apple-layout-guidance], [Kobo fixed-layout documentation][kobo-layout-guidance].

EPUB 3.3 itself permits `rendition:layout-pre-paginated` and `rendition:layout-reflowable` on spine `itemref` elements to override the global setting. Reading systems must process applicable spine overrides. Apple Books' narrower per-book restriction does not remove the standard's mixed-layout capability. Manifest resource identity/type/properties, spine layout overrides and global rendition metadata are distinct inputs. [Layout overrides][layout-overrides], [reading-system spine overrides][spine-override-processing].

**Pinned code facts:** The parser retains spine `properties`, but section construction only projects page-spread placement from them; `view.js` chooses one renderer from the book-level layout. The legacy branch reads the Apple display-options file first, falling back to Kobo only if the Apple XML is absent. `fixed-layout=true` fills an unset global layout with `??=`; it does not replace an explicit OPF value. `open-to-spread=false` can supply initial page-side placement. The helper reads two named options, not an implementation of every vendor extension or platform-specific rule. [Sections and legacy precedence][sections], [option and page-spread helpers][legacy-layout-helpers], [renderer selection][renderer-selection].

The manifest projection also omits the `fallback` attribute. The cited loader dispatches by media type, without traversing a manifest fallback chain. The standard requires supported fallback selection, or an alert if no alternative is supported; retaining a `mathml`/`svg` flag does not implement that path. [Manifest projection][parser], [resource dispatch][resource-policy], [manifest fallback processing][manifest-fallback-processing].

**Inference and unverified behavior:** Legacy hints offer a detection path, not proof of legacy fixed-page fidelity. Mixed-layout books still need an explicit Q6 outcome and, if required, per-section adapter work. Later fixtures would need to distinguish vendor-only EPUB 2 hints, EPUB 3 metadata, conflicting hints and genuine mixed-layout spines. Apple also documents fixed-page continuous scrolling via `rendition:flow=scrolled-continuous`; that is a separate presentation behavior from vertical writing and is not established by Foliate's fixed-page/spread path. Q7 remains open. [Apple layout guidance][apple-layout-guidance], [fixed layout][fixed-layout].

### Resource/page bookmarks without a text selection

**Direct facts:** CFI is not restricted to text ranges: it can address structural elements, including an image, and defines spatial offsets. It even defines character offsets into an authored HTML `<img alt>` attribute. Therefore, inability to select depicted words does not mean the standard cannot locate the image or its containing resource. These syntactic capabilities do not establish an adapter's support for them. [CFI 1.1 path resolution, character/spatial offsets and examples][cfi-structural-locations].

**Pinned code facts:** Each section carries its resource href and an OPF spine CFI. Fixed-layout relocation reports a section index with `range: null`; `getCFI(index, null)` returns the base section CFI, and `lastLocation.source` records the section href. Href navigation resolves a resource to a spine index, and fixed navigation maps that section to a spread and side. These are page/resource location seams that do not require a text quote. [Section records][sections], [relocation][resource-relocation], [base CFI][base-cfi-navigation], [href resolution][resource-href-resolution], [fixed navigation][fixed-page-navigation].

Two gaps prevent calling this a validated bookmark round trip. `goToSpread` for the already loaded spread calls `#render(side)` and returns without updating `#side` or emitting relocation; its reported current section can therefore disagree with the requested side. Separately, browser bookmarks currently send only `cfi` and `title` under a book ID, without a verified-source revision field in that request. [Same-spread branch and location reporting][fixed-page-navigation], [bookmark client][bookmark-client], [bookmark DTO][bookmark-input]. The CFI-to-DOM-Range code uses DOM containers/offsets without a special `img alt` interpretation, so the specification's alt-text offset feature is not established by this implementation. [CFI range conversion][cfi-range-conversion].

**Inference:** A source-bound resource/page bookmark could identify the verified publication revision, package/spine occurrence and normalized resource href, with a base CFI as an engine locator. Its target would be the actual fixed resource, not a screen page number, reading percentage or transient spread pairing. One source document can itself depict a two-page spread; this does not create two independently identified resources. Reopening such a bookmark need not claim a selected-word highlight, text-linked note, OCR result or EPUB ink surface. The existing source identity contract still applies, including explicit failure if the requested resource cannot be reached. [Source identity and note boundaries][notes], [navigation failure][navigation-failure].

**Unverified:** Correct-side reopen in LTR/RTL spreads, zoom/orientation changes, image-only resources, unreadable target handling and native/browser association. Q9 still decides whether this bookmark capability is required. No storage design or page-note exception is accepted here.

### Existing PDF annotation appearances and comment text, read only

**Direct facts:** `PDFPage.annotations` enumerates a page's annotations. `displaysAnnotations` controls page annotation drawing, and `PDFAnnotation.shouldDisplay` is respected by page drawing. If an annotation has an appearance stream, PDFKit draws using that stream; Apple warns that it can override configured attributes such as stroke color. This supports a visual path for existing appearances, with display flags and stream behavior as documented qualifications. [Annotation enumeration][pdf-annotation-list], [page drawing switch][pdf-display-annotations], [per-annotation visibility][pdf-annotation-visibility], [appearance streams][appearances].

Reading comments is a separate path: `PDFAnnotation.contents` returns associated textual content, if present. Apple's `PDFAnnotationKey.contents` documentation explicitly describes a human-readable alternative for non-text annotations, including VoiceOver speech. `popup` exposes an associated pop-up annotation and its bounds/open state; Apple says pop-ups are not used with links or widgets. A painted highlight, ink stroke or note icon alone consequently does not establish that a reader can discover and read its comment. [Associated comment text][pdf-comment-contents], [contents accessibility meaning][pdf-comment-key], [pop-up association][pdf-comment-popup].

**Inference:** A read-only UI could enumerate annotations on the relevant page, associate available comments with their marks and expose the text to VoiceOver, while leaving the original PDF and BookOrbit sidecars separate. The getters and drawing APIs do not require editing, flattening or importing embedded annotations into personal notes. That does not prove an automatic, complete PDFView comment interface. Appearance presence, comment availability and discoverability are separate checks; an absent `contents` string does not prove that a visible annotation is missing, and a present string does not prove a faithful appearance. [Immutable PDF ownership][immutable-pdf], [annotation and comment APIs][pdf-annotation-list].

**Permission caveat:** Apple distinguishes `allowsCommenting` for creating/modifying document annotations, `allowsCopying` for copying to the Pasteboard and `allowsContentAccessibility` for accessibility extraction. They are not interchangeable gates or fidelity guarantees. Apple notes that copying permission is separate from locked/unlocked state, that an encrypted PDF may open with an empty password, and that the app enforces the declared copying permission. These facts do not expand the accepted ordinary-unprotected-file scope or settle a new permission policy. [Commenting permission][pdf-comment-permission], [copying semantics][pdf-copy-permission], [accessibility extraction permission][accessibility-permission].

**Unverified:** Actual supported annotation appearances/subtypes, missing or stale appearances, sticky-note/highlight comment discovery, comment VoiceOver and focus return on the selected iPadOS version. The cited Apple APIs do not establish universal rich-text/reply-thread or attachment fidelity. Q10 remains the choice between read-only viewing of existing marks/comments and any later import/edit workflow; accepting static PDFs did not answer it.

### Available-text PDF VoiceOver and multi-column reading order

**Direct facts:** W3C PDF3 applies to tagged PDFs and distinguishes tag order, order within tags and focus order. It describes the failure where columns are read across rows instead of down each column, and calls for checking actual screen-reader output or the accessibility API. Tags can themselves be wrong. Apple's page-string APIs describe text extraction, not a guarantee of tag-tree interpretation or meaningful speech order. [W3C PDF3][tag-order], [PDFPage text][pdf-page-string]. Apple calls for proficient VoiceOver testing of supported devices and common tasks, with complete, logical navigation and readable visible text. [Apple VoiceOver evaluation][voiceover-evaluation], [Apple testing guidance][voiceover-testing].

**Acceptance implication, not a new scope decision:** A concrete way to observe the already-required available-text contract is to use known-text tagged and untagged multi-column fixtures with an independently recorded meaningful reading sequence. Include a tagged example whose logical order differs from painting order. With VoiceOver on the intended iPad/OS, read the available paragraphs in that sequence without omissions or cross-column interleaving, move between pages and navigate exposed headings/links where authored. Reach reading notes and controls, then return to the intended page/content without losing focus. If existing comments become required, include discovering and reading them. Record fixture identity, app/OS versions, actual speech/order failures and the human result. This is proposed future verification, not a claim that these checks ran or that every untagged document can pass. [Reading-order check][tag-order], [task-based device testing][voiceover-testing].

**Inference and unverified behavior:** A tag's presence, non-empty extraction or `allowsContentAccessibility=true` cannot stand in for that observation. No cited Apple contract proves that PDFKit follows every tag tree or repairs arbitrary untagged layouts. A text-bearing page that VoiceOver skips or reads in a meaning-destroying order fails the required available-text check; labelling the book partial can communicate the limitation but cannot convert it into an image-only/no-text success. Required coverage of difficult documents remains a human profile decision. No OCR, PDF remediation, tag rewriting or alternative engine is selected.

This supplement used public primary documents and pinned source inspection only. It establishes no device, browser, runtime, accessibility or private-library result. Q6-11 remain unanswered, including the warned-readable-font-fallback choice in Q8, which this narrower supplement does not reassess.
