# Start here: personal BookOrbit iPad reader

Complete planning handoff for [Agree the complete reading journey and build-readiness criteria](https://github.com/mooneeb/bookorbit/issues/13), part of [Find the design for a personal BookOrbit iPad reader](https://github.com/mooneeb/bookorbit/issues/1). This document assembles the confirmed decisions and acceptance requirements. The linked journey decision records final shared-understanding confirmation and current handoff status. It is not a production acceptance result or implementation authorization.

## Intended experience

Open a chosen book on the iPad, read comfortably, make a note with the Apple Pencil Pro, and keep reading. Downloaded EPUB and PDF reading and note editing work without the server. Reconnection sends complete note revisions to the self-hosted BookOrbit and refreshes the Mac/Android browser reader and both note lists. The iPad preserves editable handwriting; the browser displays it and edits typed text.

EPUB notes belong to exact selected words and can contain text, an editable handwriting canvas, or both. They open beside the reading context and stay associated through reflow. PDF page ink remains directly visible on the page while reading. Writing mode controls Pencil input; with it on, fingers still navigate. The native Apple tool picker and supported system settings govern Pencil behavior.

The app also provides native browsing/search, chosen downloads, notes and sync status. Advanced connected book management opens existing BookOrbit pages inside the app for all server-supported formats. Server/user/Kobo administration remains on the website. Existing whole-book personal notes and journals remain online features with their own owners.

## Supported environment and boundaries

- Main physical target: iPad Air 13-inch (M2), Apple Pencil Pro, user-confirmed iPadOS 26.6.1. The chosen deployment minimum is 26.0; do not require an OS update or silently introduce 27-only archive/input behavior.
- Server: the existing HTTPS BookOrbit at books.mooneeb.dev, with declared compatible capabilities. Offline reading does not require server reachability; sync/management do.
- Recorded browser acceptance baselines: Mac Chrome 155.0.8059.85, Mac Vivaldi 8.2.4133.89, and Oppo Find X9 Pro with user-reported Android 17 and Chrome 155.0.8059.84. Record versions again when running future checks; these numbers are historical baselines, not a claim that they remain the latest releases.
- Initial native reading: ordinary, unprotected EPUB and PDF. DRM/password protection, native reading of other formats, arbitrary EPUB page ink, book-page/handwriting OCR and native apps for other devices are outside the selected scope. Management of other server-supported formats remains available online.
- The [confirmed publication-support model](decisions/publication-profiles.md) records the eleven accepted scope choices: uniform reflowable/fixed EPUBs and horizontal LTR/RTL/mixed content, static rich content/fonts, static text/scanned PDFs, image-only EPUB page bookmarks, read-only source PDF comments and explicit partial reading. Its linked resolution records complete-model confirmation.
- The first export requirement is an unencrypted app recovery file with notes, bookmarks, context, pending/recoverable state and a download list, excluding complete books and credentials. New readable PDF/text reading-note exports are outside scope. Existing website exports remain existing features.
- Automatic unmerge, public App Store distribution and an offline library-management queue are outside the first version. Background sync/renewal has no unconditional completion guarantee.

## Specification readiness and app acceptance

Specification readiness means that required behaviors, ownership, technical boundaries, refusal/recovery states and acceptance criteria are concrete and traceable, with no unassigned core choice hidden behind a prototype result. It does not mean production code, migrations, integrations or performance/restore tests have passed.

Daily-use acceptance requires the implemented system to satisfy its mandatory scenarios on the supported devices and declared dataset/profile. Required workflows include both reading formats, offline notes and automatic browser arrival, full online book management, accessibility, private ownership, maintenance and recovery. A feature cannot be silently deferred because the reader prototype did not exercise it. The [technical fault and operational matrix](acceptance/technical-and-operations.md) carries the required contract, migration, ownership, lifecycle, management, packaging, recovery and scale checks with links to their policy owners.

The [accepted complete-journey review choices](https://github.com/mooneeb/bookorbit/issues/13#issuecomment-6374170330) require at least thirty minutes of reading per format, private copies from the actual library alongside controlled fixtures, and every mandatory workflow passing before daily use. Documented minor cosmetic defects may remain only with no known data-loss, privacy, anchoring, recovery or required-accessibility failure. Cosmetic classification cannot defer a required function or dismiss unreadable handwriting.

The [storage acceptance matrix](decisions/storage-recovery.md#recovery-order-and-acceptance-targets) owns numeric scale, latency, memory, backup and recovery conditions. Repeat those measurements under declared conditions, without replacing them with an easier dataset or percentile inferred from one capture. Fault and boundary cases require their exact correctness outcomes.

Implementers must declare and verify exact schemas/DTOs, shared/native transport fixtures and generated migrations within those owners; current legacy endpoints cannot be assumed to implement the new contracts. Missing execution evidence is future required work. A newly discovered product/architecture trade-off becomes a precise decision before changing the accepted model.

The daily-use evidence report must identify every required case/variant and outcome, actual environment/source/profile measurements, the human thirty-minute verdict for each format and any remaining cosmetic defects. It must preserve failed/blocked evidence and earlier fixture limitations. Source-level tests, document checks, tags/parser flags and a mocked transfer cannot replace the relevant physical, browser, recovery or usability observation.

## Planning completion and implementation boundary

The final shared-understanding review covers this assembled specification, confirmed policy index, standalone scenarios, technical/operational gates, supported/excluded profiles, failure/recovery behavior and evidence limits. Its confirmation settles this complete-journey decision. Once no open child or in-scope fog remains, the map can be completed as a planning handoff. The canonical final status remains in the linked journey decision/map, rather than an independently maintained document status.

No core choice is intentionally deferred behind an unspecified later improvement. Ordinary implementation details follow these contracts. A failed mandatory requirement remains a release blocker; a newly exposed incompatible design cannot be silently accepted by relabelling it partial or cosmetic.

Planning completion authorizes no production implementation, real book merge, server update, backup/restore, private-book access or app installation. A later implementation task can use this handoff and retained fixture evidence without treating the production app as already built or accepted.
