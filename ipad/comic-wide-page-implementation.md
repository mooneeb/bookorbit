# Native wide comic pages

The production native comic reader now applies the canonical `widePageSingletonMode` preference. In paged facing-page mode, automatic layout presents genuinely wide delivered pages alone. Narrow pages beside a wide page or at the end of a comic retain a half-width slot and a real empty slot, on the correct side for left-to-right or right-to-left reading. Cover and shifted alignment retain their existing singleton prefixes. Disabled adaptation pairs pages normally. Single-page and continuous modes remain single-page layouts.

The native and web readers share `CBX_WIDE_PAGE_RATIO_THRESHOLD` from the types package. Image classification uses the dimensions of the already delivered, orientation-adjusted thumbnail; it adds no requests to inspect unvisited pages. Classification retains only page indices, bounded by the existing 100,000-page reader limit. Decoded images still use the existing bounded visible window. Learning a wide page updates cached normal and shifted layouts, and waits until any active animated transition finishes. The current logical page remains the reader position when the visual groups change.

Facing layout stores runs between observed wide pages instead of constructing a controller, image or entry for every page. Page and visual-unit lookup use binary search over those runs. PDF and comics without discovered wide pages retain the existing constant-time pair formulas. Cached geometry is rebuilt only after discovering new wide pages, rather than during every reader view update. The maximum sparse geometry and classification memory, transition costs and layout stability still require runtime measurements.

Reader settings now load this field from canonical per-book and default responses, validate its vocabulary, send it only when changed, and unset it when restoring defaults. The existing server/account-scoped local preference storage retains it when synchronization is disabled. Native settings expose both automatic singleton presentation and keeping wide pages in pairs.

Shared types and plugin-API builds, generated-contract freshness, server production typechecking, frontend typechecking and full frontend ESLint pass. Complete-concurrency Swift 6 typechecking of the actual reader dependencies with warnings treated as errors also passes, as does the full production native build for both simulator architectures. Strict Swift formatting, parsing, Node syntax, Prettier and diff checks pass.
